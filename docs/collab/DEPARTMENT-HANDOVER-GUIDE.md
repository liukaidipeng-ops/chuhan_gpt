# 技能新象棋｜八部门接管与协作指南

版本：2026-10-12  
适用对象：总协调、TD（技术总监）、优化部、美术总监朱墨、声音部、楚汉数值部门Balance、角色部、顾问部advice、CG组。  
项目：私有仓库 `liukaidipeng-ops/chuhan_gpt`。原 `chuhan_v01` 和 Claude 原仓库只读。

## 1. 总原则

本指南承接 Claude 时期的职责分工、审核标准、交付方法和项目经验，同时以当前用户明确指令和当前工作区记录为准。旧文档里的 Claude Artifact 链接、旧会话编号、旧分支状态、旧暂停日期和旧审批状态都只是历史资料；不得当作当前入口、当前授权或当前进度。需要时先核对新仓库、当前审批台和真实材料。

任何部门收到明确任务后，都要在本轮启动可执行工作，不以“已收到”、计划、待办或转发消息代替执行。依赖未到时，先做不依赖它的检查、准备或方案。报告必须区分进行中、等待外部结果、受阻、已完成，并给出证据、下一动作和由谁执行。只有实际启动且仍在运行的任务才能称为后台进行中。

## 2. 绝对审批规则：聊天里永远不拍板

**凡是需要用户作出决定、选择、批准或否决的事项，必须先在当前审批台建立审核卡，并附上足以判断的材料。永远不要在聊天里向用户索要拍板，也不得把聊天中的“好”“可以”“选甲”等内容当成审批结果。**

当前唯一用户审批入口：<https://chuhan-review-desk.alivevale513.chatgpt.site/>。

- 文字、规则、数值、玩法方向、优先级、范围或授权：在审批台用清晰选项建卡。
- 视觉、棋子、界面、模型、动画、分镜：附图或视频，说明版本和差异。
- 声音、配音、音乐、音效：附可播放素材，并标注场景、时长或对比项。
- 代码/仓库授权：写明目标仓库、精确分支或提交、拟做操作及其边界；没有明确授权不能扩大范围。
- 审核材料尚未准备好：先完成材料；不得用空卡、模糊卡或聊天问题代替。

卡片创建后，聊天只可提示入口和件数，例如：“有 2 件待审，请打开审批台：<https://chuhan-review-desk.alivevale513.chatgpt.site/>。”聊天不能包含要求用户选择的题目，也不能要求用户在聊天回复决定。用户如果在聊天里误发了选择，部门应礼貌告知审批台入口，并请其在卡片中提交；在审批台收到真实提交前保持待审，不执行该决定。

收到审批台提交后，责任部门必须重新读取实际卡片及提交内容，逐件写入真实回执（时间、准确理解、下一动作），并核对页面显示“已收到”。聊天只报告收件状态和处理进度，不复述问题要求用户再确认。页面通知失败时，说明事实并继续按允许的替代路径排障；不能谎报“已通知”或“已回执”。审批台不可用时，先排查并向总协调反馈技术故障；不得退回聊天拍板。

不需要用户决定的常规技术细节，由负责部门在授权范围内自行判断并记录依据，不要为了形式制造审批卡。判断是否需要用户决定时拿不准，先暂停那项不可逆/方向性选择，做独立准备并由总协调检查审批台和项目记录；仍需用户决定就先建卡。

| TD（技术总监） | 游戏代码与规则集成、构建、测试、PR、发布 | 检查授权范围、回归结果、变更清单；只有明确授权才发布 |

总协调本身不是第九个专业部门。部门聊天是独立工作入口，不等于任务已自动运行；对话只有在明确接到任务并实际执行后，才可报告在做。

## 4. 开工、推进和跨部门交接

### 4.1 先入制作表，再按优先级开工

部门获得新任务、发现衍生任务或预计后续要做某项工作时，第一动作是向总协调汇报。汇报必须写明任务编号、目标、为什么要做、建议负责人、依赖、交付物、验收证据和不做的影响。部门不得自行决定它比当前任务更优先，也不得因为“顺手”就扩大实现范围。

总协调负责把任务去重、拆分依赖并录入 `docs/collab/PRODUCTION-BOARD.md`。用户在制作表填写优先级后，总协调向责任部门发送正式开工命令。优先级为：`P0 立即阻断`、`P1 当前主线`、`P2 下一批`、`P3 候补`、`HOLD 暂缓`、空白待排序。

未收到正式开工命令时，部门只可进行只读核查、复现、素材盘点和风险说明；不得修改共享代码、训练、合并或发布。已经获批并在实施的任务继续执行，由总协调补录。遇到数据丢失、生产中断、误写原仓库等紧急风险时先止损，并立即升级总协调补录 P0。

总协调下发任务时必须给出编号、优先级、负责人、协作部门、范围、验收证据、依赖和完成定义。部门完成、受阻或发现新增范围时立即回报总协调，由总协调更新制作表。部门不得自行改优先级或转交责任。

总协调负责持续巡检：是否漏录任务、是否少做验收项、是否有跨部门依赖无人接、是否有明确任务却无实际动作。当前巡检采用半小时周期，只检查有活跃任务的部门；没有任务的部门不做空巡检。任务增减时由总协调同步调整巡检名单。

每项任务开工前：

1. 查看制作排期表、总表 Issue #1、新评论和该任务已有的审批卡、回执及附件，确认优先级和总协调开工命令。
2. 阅读本指南及对应部门接管记忆/专业工作流；引用旧 Claude 资料时同时核对新仓库文件、分支和时间，避免旧记录覆盖新证据。
3. 复述任务目标、负责人、范围、验收方法和下一动作。若已有授权，立即开始可逆且必要的工作。
4. 发现需要用户决策时，先准备材料并送入审批台；同时继续所有不依赖该决定的工作。
5. 交付时回到总表记录证据。跨部门消息以任务单或仓库文件保存正文，消息只负责提示查看，不把提示成功等同于对方已阅读。

任务状态定义：

- **进行中**：已启动具体操作，附文件、提交、运行输出或当前产物。
- **等待外部结果**：写清等待谁、何时请求、等待什么、独立事项做了什么，以及实际安排的复查方式。
- **受阻**：保留实际错误，说明影响；先诊断并尝试安全替代，独立工作继续推进。
- **待审核**：审批卡已创建且包含真实材料，列出卡片链接/编号；未收到提交前不得写“批准”。
- **已完成**：交付确实存在且验收已执行，给出可复核证据；“发过消息/建过卡/写过计划”不能单独算完成。

任务评论/交接模板：

```text
关联总表：#1
负责人/协作部门：
目标与触发场景：
状态：
授权范围（仓库/分支/文件/操作）：
依据与现有证据：
本轮实际动作及结果：
验收方法和结果：
用户审批卡（如需）：
未完成项/阻碍/等待对象：
下一动作与执行人：
```

## 5. 统一审核卡和真实回执

一项决策一张清楚的卡。标题写部门与编号；正文包括：要决定什么、背景和影响、材料版本/链接、2–4 个明确选项及代价、推荐及理由、备注/标注入口。视觉、声音卡必须直接附可查看/播放材料。审批台历史条目可查看时直接从列表打开内容；不要求用户撤回才能复看。

提交后由指定责任部门实际打开卡片，逐条读出用户的选项、原话、备注和标注附件，再按原意执行并写回执。意见不清楚时，不在聊天追问；准备具体澄清卡并将其送入审批台。回执写入审批台，聊天只提供件数、收件/未收件状态及入口。

## 6. 实施、代码边界与验收

- `chuhan_v01` 及 Claude 原仓库始终只读：不改文件/分支/设置/历史，不从该目录进行提交或推送。
- 所有新改动只进入私有 `chuhan_gpt` 副本或其经授权的独立工作区。仓库、分支、提交不明确时先只读核验。
- 各专业部门在职责和被授权范围内准备补丁与证据。共享工作副本不得并发写入；协调好负责人和文件范围后再整合。
- 原仓库外部写入、公开发布、收费资源、长时间 AI 训练、合并或生产发布不得从一般开发授权推断；执行前必须有明确范围授权。授权本身若需用户拍板，按第 2 节送审批台。
- TD 接手前检查：提交差异、构建、相关测试、回归证据、目标仓库/分支、用户审批记录及已知缺陷。失败项和未测范围如实保留，不能靠文字声明代替验证。
- 对批准过的版本保留其审批卡、素材版本和具体提交之间的对应关系；改动实质内容后重新判断是否需要再次审批。

## 7. 从 Claude 资料迁移时的核实规则

Claude 资料提供专业背景，不自动提供当前授权。接管记忆和旧工作流应保留原意、标出来源与日期，并分别标明：

1. 长期有效的职责、技术事实和用户偏好；
2. 仅适用于旧 Claude Artifact、会话、分支或自动提醒的操作步骤；
3. 已由新指令取代的规则；
4. 仍需从新副本、审批台或真实测试核实的状态。

旧审批已批准且有真实证据的，不重复要求用户审批；只有编号或描述而找不到提交数据时标“待核实”，不补造审批。旧暂停日期不得覆盖用户之后明确解除的命令。当前审批入口以第 2 节唯一网址为准。
